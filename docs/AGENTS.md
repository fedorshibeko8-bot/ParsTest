# Правила работы ИИ-агентов над проектом

Документ обязателен к прочтению перед любой задачей. Цель — чтобы несколько агентов работали последовательно и не мешали друг другу.

## 1. Порядок чтения

1. `ТЗ.md` — что требуется (единственный источник требований).
2. `TASKS.md` — что уже сделано и что свободно.
3. `docs/AGENTS.md` — этот файл (правила).
4. `CHANGELOG.md` — история изменений и принятые решения.

## 2. Как брать задачу

- Бери самую младшую задачу со статусом `todo`, у которой **все зависимости `done`**.
- Перед работой: поставь `in_progress`, впиши модель/агента и дату в «Исполнитель».
- Если задача уже `in_progress` другим агентом — не трогай её, бери следующую свободную.
- Если не хватает данных/ключей — переведи в `blocked`, опиши чего не хватает в «Результат», добавь запись в `CHANGELOG.md`. Не выдумывай секреты и не вставляй фейковые токены в код.
- Не переписывай чужие готовые модули «по вкусу». Улучшения — отдельной задачей.

## 3. Технические рамки (жёсткие)

- **Python 3.12**, **aiogram 3.x**, **SQLite**, **long polling**. Никаких вебхуков, доменов и SSL.
- **Windows для локальной разработки и DRY_RUN-проверок; Bothost — подготовленный дополнительный Linux/Docker-путь.** Для него используются только описанные в `DEPLOY_BOTHOST.md` настройки; фактический внешний деплой выполняется лишь по явному решению владельца. Вебхуки и изменение логики публикации не добавлять.
- Секреты — только `.env` (в git не попадает). В репозитории живёт `.env.example` с заглушками.
- Весь код должен **запускаться и не падать без реальных ключей** (`DRY_RUN=1`, заглушки провайдеров ИИ, мок-отправка в канал).
- Минимум зависимостей: ориентир ~100–150 МБ RAM. Тяжёлые SDK не тащим — Gemini и Groq через `httpx` REST. У Linux/Docker deployment dependencies должны оставаться без pytest и dev tools.
- Без LLM там, где ТЗ запрещает: фильтрация новостей, дедупликация, проверка фактов.
- Логи — в файл с ротацией по дням, хранение 30 дней. Пользовательские тексты в логи целиком не пишем.

## 4. Структура проекта

```
bot/
  main.py            — точка входа, long polling
  config.py          — чтение .env, валидация, дефолты
  db.py              — SQLite: схема, миграции, запросы
  models.py          — dataclass'ы/типы (Post, статусы)
  parsers/rss.py     — источники, опрос, jitter
  filters/keywords.py— отбор по ключам
  filters/dedup.py   — 3 ступени дедупликации
  services/queue.py  — очередь, TTL, тайм-ауты, перехват
  services/media.py  — картинки: скачать/удалить
  services/ai.py     — Gemini/Groq + заглушка
  services/publisher.py — публикация в канал
  handlers/admin.py  — команды и личка админов
  handlers/callbacks.py — инлайн-кнопки, карточка поста
  utils/logging.py   — настройка логов
data/                — runtime: bot.db, images/ (в git не попадает)
tests/               — юнит-тесты (pytest)
setup.bat, run.bat   — запуск на Windows
```

Отклонения от структуры допустимы, но фиксируются в `CHANGELOG.md`.

## 5. Стиль кода

- `async/await`, `asyncio.create_task` для планировщика, без блокирующих вызовов в хендлерах (сеть — `httpx.AsyncClient`, диск — `asyncio.to_thread` при тяжёлых операциях).
- Типизация, короткие функции, docstring на русском.
- Ошибки внешних сервисов не роняют бота: логируем + retry/backoff там, где уместно.
- Пользовательские сообщения — по-русски, эмодзи допустимы в меню (см. ТЗ).

## 6. Git и коммиты

- Ветка по умолчанию — `main`; для крупных задач можно `feat/T0X-кратко`, затем merge.
- Сообщения коммитов: `T0X: что сделано` (например, `T03: RSS-парсер и опрос с jitter`).
- В коммит не попадают: `.env`, `data/`, `.venv/`, `__pycache__/`, логи.
- Один коммит = одна задача (или логически цельная часть задачи).

## 7. Обязательный минимум приёмки задачи

- Код запускается локально на Windows (хотя бы в `DRY_RUN=1`).
- Нет синтаксических ошибок: `python -m compileall bot`.
- Для логики — юнит-тесты там, где это разумно (фильтр ключей, дедупликация, шаблон публикации).
- Обновлены `TASKS.md` (статус + результат) и `CHANGELOG.md` (что, кто, файлы).
- Если менялось поведение по сравнению с ТЗ — записано в «Решения» `CHANGELOG.md` с причиной.

## 8. Ограничения по данным

- Тестовые фикстуры (RSS-выгрузки, примеры статей) — без персональных данных.
- Картинки из RSS — только для публикации; не хранить дольше 48 ч после публикации/дропа.
- Не загружать данные или секреты владельца в Git, образы, сторонние сервисы и тесты.
- Не менять реальную БД при проверке миграций: только отдельная копия и заранее проверенный снимок.
- Не выполнять внешний деплой, не переводить `DRY_RUN=0` и не публиковать в канал без отдельного разрешения владельца.

## 9. Передача работы

В конце задачи в `CHANGELOG.md` пиши 2–5 строк «что дальше», если следующему агенту нужен контекст (неочевидные решения, известные баги, чего не хватает).
